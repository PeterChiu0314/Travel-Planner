# Issue #27 預算協作排序

[Issue #27](https://github.com/PeterChiu0314/Travel-Planner/issues/27) 在 `codex/budget-collaboration-redesign` 新增分類內排序、跨分類插入及分類整組排序。Formal 與 Demo 共用表格和拖曳元件。Demo 排序存在記憶體，重新載入回到示例資料。

## 交易及同步

- [遷移](../supabase/migrations/20261110100000_expense_ordering.sql) 新增三張私有表，分別保存項目順位、旅程分類順序及拖曳租約。沒有既有資料回填。尚未手動排序的項目沿用原始順序，排在有手動順位的項目後面。
- 拖曳租約綁定帳號、分頁與能力權杖，30 秒到期。開始與結束使用 `expense_signals` 觸發範圍內的快照更新。協作者以快照中的截止時間清除遠端標示。切離頁面、取消或失聯時嘗試釋放，逾時亦可恢復。
- 同一旅程的寫入沿用既有交易鎖。後端以來源版號、分類版號和前後錨點重新求值。跨分類才更新分類欄位與其 revision，且有效的分類編輯租約優先。排序確認會查原始 request ID，查無提交時寫下拒絕收據，封住延遲送達的寫入。
- 已付款項目可以排序及移分類，沿用原本的金額、分攤、代付、連結與匯率。旅程刪除由現有交易帶走排序資料。

## Staging 手測

以兩個有編輯權限的帳號開啟同一測試旅程，準備同分類兩筆支出、一筆已付款支出及一個空分類。使用 [Staging Preview](https://travel-planner-git-codex-budget-co-6eda5b-peter-chiu-s-projects.vercel.app) 並先核對 Preview SHA 與遷移版本 `20261110100000`。

1. 將項目拖至同分類另一列之前及之後，再跨分類插入指定列。收合空分類後把項目拖到它的標題，展開確認排在末端。拖動分類標題，刷新兩個帳號並比對分類與子項目順序。旅行中也可在預算／實付視圖確認共同排序。
2. A 拖起項目時，B 查看原位的單一外框、左側同色 Move 圖示與 hover 頭像。B 選取該列或編輯備註，並試拖另一筆。用相同步驟測試分類標題，確認其子項目仍可拖曳。
3. B 持有該項目的分類編輯權限時，A 先在原分類排序，再嘗試跨分類。前者應成功，後者應回復並提示。B 完成或放棄分類編輯後，A 應能重新拖曳。
4. 用 Escape、切換頁籤和斷線分別取消，確認把手恢復。A 放下時若斷線，重連後確認畫面依原請求收斂。搜尋、付款篩選或多選期間，把手應停用。
5. 比對已付款支出移動前後的金額、參與者、付款人、行程連結、匯率與結算。檢查滑鼠、鍵盤及手機上從把手拖曳、從表格其餘區域捲動。

本機驗證包含 [隔離 SQL](../tests/expenseOrdering.test.mjs) 與 [雙帳號及 Demo Chromium](../tests/expenseOrdering.spec.js)。隔離 Chromium 使用 SQL 後端與 Realtime 事件替身，線上帳號與 WebSocket 由 Staging 手測驗收。

## 桌面手測補修

拖曳項目時，把一列高度從來源移到目標的 Ghost Card。整組分類使用來源分類的高度，目標的標題和所有可見項目都參與前後判定。放手後由移到目標的實際列接替 Ghost，等待權威快照期間維持該位置。明確拒絕或取消時回到原位。開啟減少動態效果時，仍保留目標空間和 Ghost。

編輯器與外層快取都檢查 `snapshotRevision`。延遲的舊回應不會發布，也不會改寫離線排序快取。

桌面補驗以 Ghost、整組命中範圍和放手後的連續性為主。原桌面手測未遇到空分類，該項列 N/A。線上雙帳號與實機觸控仍待人工驗證。
